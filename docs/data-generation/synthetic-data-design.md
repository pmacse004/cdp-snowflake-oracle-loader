## 3. Synthetic Data Design Principles

### 3.1 Personal Information
- **Names:** Drawn from a fixed 50×50 first×last name pool. All names are obviously invented (e.g., _Horatio Ashworth_, _Ophelia Stonebridge_). No real person can be identified.
- **Emails:** Use RFC 2606 reserved domains `@example.com` and `@synth.invalid` exclusively. No real email address is ever generated.
- **Phone numbers:** Use the range `555-0100` through `555-0199` exclusively. This specific 100-number block is the only range formally reserved by the North American Numbering Plan Administration (NANPA) for fictional/dramatic use. The claim that all `555-xxxx` numbers are reserved is incorrect — only the 100-number range `555-0100` to `555-0199` is specifically set aside. Formula: `'555-' || LPAD(100 + MOD(ABS(HASH(…)), 100), 4, '0')`. No real phone number is generated.
- **Dates of birth:** Synthetic, derived from a hash function, no real birth date.
- **SSN / Tax IDs:** Not generated. The source table has `SSN_LAST4` and `TAX_ID` columns; both are left NULL.

### 3.2 Addresses
- **Street numbers:** Computed from a hash modulus (100–9999 range).
- **Street names:** 30 entirely fictional names (Sunridge, Millbrook, Clearwater…).
- **Cities:** 20 obviously synthetic names (Synthport, Demoville, Testburg, Faketon…).
- **State codes:** Cycle through 10 real US state codes (`TX, CA, FL, NY, IL, PA, OH, GA, NC, MI`) — real codes, but attached to synthetic city/street combinations.
- **ZIP codes:** Synthetic 5-digit values derived from hash.
- **Counties:** Synthetic (Synth County, Demo County…).
- **Coordinates:** Synthetic values near the US geographic centre (39.5°N, -98.4°W) ±offset derived from hash. Not real property coordinates.

### 3.4a DEMO_AS_OF_DATE — Demo Anchor Date (Issue #9)

All date arithmetic in Phase 3 scripts is anchored to a single session variable `$DEMO_AS_OF_DATE` set in script 05:

```sql
SET DEMO_AS_OF_DATE = DATE_TRUNC('MONTH', CURRENT_DATE());
```

- Default value: the 1st of the current calendar month (e.g., `2025-06-01`).
- Can be overridden with a literal date: `SET DEMO_AS_OF_DATE = '2025-06-01'::DATE`.
- Downstream scripts 06, 07, 08, 09 all use `$DEMO_AS_OF_DATE` instead of `CURRENT_DATE()` so re-runs on different calendar days produce the same billing months, the same account creation dates, and the same historical billing periods.
- `CURRENT_TIMESTAMP()` is still used for `CREATED_AT` / `UPDATED_AT` on **daily and monthly simulation** records (scripts 08 and 09) so that incremental watermarks are strictly greater than initial-load watermarks.

## 4. Generation Method

All data uses Snowflake built-in functions for deterministic generation:

| Technique | Usage |
|---|---|
| `TABLE(GENERATOR(ROWCOUNT => N))` | Generate N synthetic rows |
| `SEQ4()` | Monotonic sequence within a generator set |
| `ROW_NUMBER() OVER (ORDER BY ...)` | Stable row numbering |
| `HASH(seed_string)` | Deterministic pseudo-random value from a seed |
| `MOD(ABS(HASH(seed)), range)` | Bounded deterministic value |
| `LPAD(value, width, '0')` | Zero-padded ID formatting |
| `DATEADD / DATEDIFF` | Date arithmetic |
| `TRY_TO_DECIMAL(path::STRING, p, s)` | Safe JSON VARIANT → NUMBER |

Using `HASH(stable_id || 'salt')` ensures the same customer always gets the same deterministic attribute (e.g., same city, same rate class, same billing cycle) across reruns.

## 5. Relationship Integrity

The generation scripts build records in strict parent-to-child order:

```
REF.CODE_VALUE (script 05)
    └── CUSTOMER.CUSTOMER (script 06)
            ├── CUSTOMER.CUSTOMER_CONTACT
            └── CUSTOMER.ENERGY_ACCOUNT
                    ├── CUSTOMER.BILLING_ACCOUNT
                    └── SERVICE.PREMISE
                            ├── SERVICE.METER
                            └── BILLING.MONTHLY_USAGE
```

Every foreign key is satisfied before child rows are inserted. The `IF NOT EXISTS` / `WHERE COUNT(*) = 0` guards prevent double-load.

## 6. Idempotency and Reset

### 6.1 Idempotency
- All INSERT statements use row-count guards (`WHERE (SELECT COUNT(*) FROM table) = 0`)
- UPDATE guards check `UPDATED_AT < DATEADD(MINUTE, -5, CURRENT_TIMESTAMP())` to avoid re-updating recently changed rows
- Daily batch uses prefix `CUST-D1-`, `EA-D1-`, etc. so reruns check for existing prefix rows

### 6.2 Reset
- `11-reset-demo-data.sql` deletes all rows in child-to-parent order
- Does NOT drop any schema object, warehouse, user, role or key
- Guards verify `CURRENT_DATABASE = CDP_UTIL_DB` and `CURRENT_ROLE = CDP_ADMIN_ROLE`
- DELETE statements are commented out and must be manually uncommented

## 7. Scalability Notes

The current design generates ~10,000 customers and ~31,500 usage records. To scale toward the 1 million target mentioned in Phase 1 non-functional requirements:

1. Increase `GENERATOR(ROWCOUNT => 1000000)` in `06-generate-initial-data.sql`
2. Use a larger warehouse (`MEDIUM` or `LARGE`) for the generation run
3. The ID padding (`LPAD(..., 6, '0')`) supports up to 999,999 rows before overflow — extend to 9 digits for 1M
4. No redesign of schema, views or ETL pipeline is required
5. Oracle Flyway migrations and Spring Batch job definitions are unaffected

## 8. Known Assumptions

| ID | Assumption |
|---|---|
| DA-01 | Snowflake `HASH()` function produces sufficiently uniform distribution for demo purposes |
| DA-02 | `SEQ4()` within a `GENERATOR` is monotonically increasing within a single query but not guaranteed globally |
| DA-03 | Rate plan JSON keys are lowercase (`fixed`, `energy`, `demand`, `tax`) matching `TRY_TO_DECIMAL` extraction in `04-create-export-views.sql` |
| DA-04 | Monthly usage billing months are computed relative to `CURRENT_DATE()` at execution time — reruns on different dates produce different billing months |
| DA-05 | The `11-reset-demo-data.sql` script requires the Snowflake session's `TIME_TRAVEL_RETENTION_PERIOD` to be set appropriately if undrop/recovery is needed |
| DA-06 | Secondary accounts (`EA-S-`, `CUST-D1-`) are generated as subsets and will not exceed 5% / 1% of primary counts |
